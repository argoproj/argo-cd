## Behavioral Improvements / Fixes

### Health Aggregation for Suspended Jobs and CronJobs

The health aggregation behavior for suspended Jobs and CronJobs has changed to better reflect operational intent.

**New behavior:**

- Suspended Jobs now contribute `Healthy` status to Application health instead of `Suspended`
- Suspended CronJobs now contribute `Healthy` status to Application health instead of `Suspended`
- The individual resource still displays its actual status (`Suspended`) in the UI
- Only the aggregation into the Application's overall health is affected

**Rationale:**

Suspended Jobs and CronJobs are often intentionally suspended for operational reasons (e.g., DR scenarios, maintenance windows, manual-trigger jobs). Marking the entire Application as `Suspended` due to these resources was misleading.

**Impact:**

- Applications with suspended Jobs/CronJobs will now show `Healthy` instead of `Suspended` (if all other resources are healthy)
- Automation relying on Application health status to detect suspended Jobs/CronJobs should instead check individual resource statuses
- To restore the previous behavior for specific Job/CronJob resources, use the annotation: `argocd.argoproj.io/health-aggregate-overrides: 'Suspended=Suspended'`

### ApplicationSet webhook responses now match the API server webhook

The ApplicationSet controller's webhook endpoint now handles requests the same way as the API
server's `/api/webhook` endpoint:

- Payloads larger than the `webhook.maxPayloadSizeMB` value in the `argocd-cm` ConfigMap (default
  50MB) are rejected with `400 Bad Request`. Previously, the ApplicationSet webhook had no payload
  size limit.
- A GHCR event that fails signature verification is rejected with `401 Unauthorized` instead of
  `400 Bad Request`.
- When a payload cannot be parsed, the response body is a generic `Webhook processing failed`
  message. The parser error is logged by the ApplicationSet controller instead of being returned to
  the caller.

If you monitor the ApplicationSet webhook's response codes or bodies, update any checks that relied
on the previous behavior.

## Other Changes

### Revoked token resync interval

`argocd-server` now reloads revoked tokens from Redis every 5 minutes instead of every 15 seconds. The interval is configurable with `ARGOCD_SESSION_REVOKED_TOKEN_RESYNC_DURATION`. See [Revoked token resync](../user-management/index.md#revoked-token-resync).
