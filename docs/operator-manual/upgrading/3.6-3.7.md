## Behavioral Improvements / Fixes

### ApplicationSet webhook responses now match the API server webhook

The ApplicationSet controller's webhook endpoint now handles requests the same way as the API
server's `/api/webhook` endpoint:

- Payloads larger than the `webhook.maxPayloadSizeMB` value in the `argocd-cm` ConfigMap (default
  50MB) are rejected with `400 Bad Request`. Previously, the ApplicationSet webhook had no payload
  size limit.
- A GHCR event that fails signature verification is rejected with `401 Unauthorized` instead of
  `400 Bad Request`.
- When a payload cannot be parsed, the response body is a generic `Webhook processing failed`
  message. The parser error is logged by the ApplicationSet controller instead of being returned to
  the caller.

If you monitor the ApplicationSet webhook's response codes or bodies, update any checks that relied
on the previous behavior.

### Repo server graceful scale-out

The repo server can now reject requests when it is at capacity so clients retry, enabling graceful
horizontal scale-out (for example an HPA on the new `argocd_repo_server_active_requests` metric). Two
opt-in settings control this, both defaulting to the previous behavior:

| Flag | Environment variable | Default | Description |
|---|---|---|---|
| `--max-concurrent-grpc-requests` | `ARGOCD_REPO_SERVER_MAX_CONCURRENT_GRPC_REQUESTS` | `0` (no limit) | Caps concurrent gRPC requests; excess is rejected with `ResourceExhausted`. |
| `--parallelism-limit-fail-fast` | `ARGOCD_REPO_SERVER_PARALLELISM_LIMIT_FAIL_FAST` | `false` | When `true`, manifest generation over `--parallelismlimit` is rejected immediately instead of queuing. |

They cover different layers, so use whichever fits (or both): `--max-concurrent-grpc-requests` is a
whole-server cap over the retryable (unary and server-streaming) RPCs, while
`--parallelism-limit-fail-fast` sheds load on the client-streaming manifest-generation path that the
gRPC limiter skips.

Clients retry `ResourceExhausted` with exponential backoff. Each repo-server call dials a fresh
connection, so DNS is re-resolved every call and newly scaled-out pods are picked up on the next
one. The remaining gap is *within* a call: against the `argocd-repo-server` ClusterIP Service the
connection is pinned to a single pod, so a retry returns to the same (possibly saturated) pod.
Pointing the client at the headless Service makes that connection round-robin across the pod IPs DNS
returns, so retries within a call spread across pods:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cmd-params-cm
data:
  repo.server: "dns:///argocd-repo-server-headless:8081"
```

The `argocd-repo-server-headless` Service ships with the bundled install manifests. If you install
Argo CD another way (e.g. Helm) and it is not present, create a headless (`clusterIP: None`) Service
selecting the repo-server pods before switching `repo.server` to it.

> [!WARNING]
> If you connect to the repo server with strict TLS (`--repo-server-strict-tls` /
> `ARGOCD_SERVER_REPO_SERVER_STRICT_TLS=true`, or a `--repo-server-ca-cert-path` is configured), the
> client verifies the repo-server certificate against the hostname it dials. Switching to the headless
> Service changes that hostname to `argocd-repo-server-headless`, so the serving certificate must list
> it as a Subject Alternative Name or the connection will fail. Add `argocd-repo-server-headless` to
> the certificate's SANs before pointing `repo.server` at it. The default (non-strict) client skips
> this check and is unaffected.

> [!NOTE]
> No action is required on upgrade. `--parallelismlimit` keeps queuing until you opt in with
> `--parallelism-limit-fail-fast`, and `repo.server` keeps using the ClusterIP Service until you point
> it at the headless one.

## Other Changes

### Revoked token resync interval

`argocd-server` now reloads revoked tokens from Redis every 5 minutes instead of every 15 seconds. The interval is configurable with `ARGOCD_SESSION_REVOKED_TOKEN_RESYNC_DURATION`. See [Revoked token resync](../user-management/index.md#revoked-token-resync).

### `--http-retry-max` now applies to TLS (and `--grpc-web`) connections

Prior to v3.7, the CLI's global `--http-retry-max` flag had no effect on TLS
connections (the default) — the retryable HTTP transport was silently discarded
during TLS setup, so retries only ever applied to `--plaintext` connections.
This is now fixed, so `--http-retry-max` retries transient failures (connection
errors, HTTP `429`, and `5xx` except `501`) for HTTP requests over plaintext or TLS,
including `--grpc-web`. (Native gRPC connections use a separate, built-in retry
interceptor that this flag does not configure.)

The flag still defaults to `0` (no retries), so behavior is unchanged unless you
have opted in. If you do set `--http-retry-max`, be aware:

> [!WARNING]
> - Retries apply to **all** gRPC-web requests, including non-idempotent ones.
>   gRPC-web tunnels every RPC as an HTTP `POST`, so the retry layer cannot
>   distinguish reads from writes. A transient `5xx` returned *after* the server
>   has already processed a mutating request (e.g. `argocd account generate-token`,
>   `argocd app actions run`) will cause the request to be re-sent. Prefer enabling
>   the flag for idempotent/declarative operations (e.g. `app set`/`app sync`), and
>   consider this before enabling it globally for mutating commands.
> - Retries add latency ahead of any command-level timeout. Backoff is capped at
>   10s per attempt, but `--http-retry-max` attempts still accumulate; size it with
>   your `--timeout` values (e.g. `app sync`/`app wait`) in mind.
